**Before you start:** read the release notes for the version you are moving to (see the [changelog](/changelog/)), and have a
working [backup process](/docs/self-hosting/backups-and-restore/).

<Steps>
1. Back up first:

   ```bash
   docker compose exec glideworth node dist/cli/admin.js backup --out /data/backups/pre-upgrade.db
   ```

2. Set `GLIDEWORTH_VERSION` in `.env` to the new version (or leave it unset for `latest`), then pull and restart:

   ```bash
   docker compose pull
   docker compose up -d
   docker compose logs --tail 50 glideworth
   ```

   Database migrations are applied automatically at start-up. Check that `docker compose ps` shows "healthy". If you build
   from source, run `git pull` (or check out the release tag) and `docker compose up -d --build` instead.
3. If it goes wrong, set `GLIDEWORTH_VERSION` back to the previous version and run `docker compose up -d`. If the database
   was changed in a way the old version cannot read, restore `pre-upgrade.db`.
</Steps>

Pin a release rather than running `latest` in production. If you have skipped several versions, upgrade one minor version at
a time and read the notes for each ([releases on GitHub](https://github.com/GlideWorth/glideworth/releases)).

<Callout type="note" title="Upgrading from Cairn">
  Glideworth was previously called Cairn. If you are upgrading an instance that still uses the old names (`CAIRN_`
  variables, the `cairn` service and `cairn-data` volume, `cairn_` keys), follow the "Upgrading from Cairn" section of the
  self-hosting guide in the repository, `docs/SELF-HOSTING.md`, before you pull the new version.
</Callout>

## What this does not do

It does not downgrade the database. Going back across a schema change means restoring a backup taken before the upgrade.
