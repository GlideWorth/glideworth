ProjectionLab and Glideworth are both financial planners that project a household's money over decades. This
page sets out what each is, using only what ProjectionLab says about itself in public and what Glideworth's
code does today. Every statement about ProjectionLab links to the page it came from and the date we read it.

## Who each suits

**ProjectionLab is the better choice if** you want a hosted planner that exists today, with a free tier and a
paid plan, from a product that has been developed since 2021 and has a public roadmap and release history and
community channels
([about](https://projectionlab.com/about), [home page](https://projectionlab.com/), read 16 Nov 2026). It also
lists an Optimize tool, added in its v4.6.0 release of April 2026, that targets federal brackets, IRMAA, ACA
limits and the NIIT cliff ([changelog](https://projectionlab.com/changelog), read 16 Nov 2026). Glideworth models
Roth conversions, IRMAA and the ACA credit too, but its tax optimiser is less developed: the project's own status
file rates its depth as partial. If you are an adviser or coach,
ProjectionLab has a Pro plan for managing clients
([pricing](https://projectionlab.com/pricing), read 16 Nov 2026); Glideworth has no adviser tier.

**Glideworth may suit you better if** you want to run the planner yourself and keep the data in one file on
your own machine, read and change the source code (AGPL-3.0), reach your plan from scripts or an AI assistant
through a server-side REST API and an MCP server, or plan across several countries with a written list of what
each country's tax estimate leaves out. You can use every feature when you self-host, at no cost.

**Neither is built around live bank connections.** Glideworth does not link accounts, by design. ProjectionLab's
security page says no linked accounts are required ([security](https://projectionlab.com/security), read
16 Nov 2026).

## Moving over from ProjectionLab

Glideworth can import a ProjectionLab JSON export. You review a report first, then apply it, either in the web
app or through the API with a dry run. The report classifies every key path in your file as mapped, ignored or unsupported, lists each
approximation or dropped field as an issue, and never prints your values.

What it does not carry over, so you should plan to check it:

- **Anything the report marks approximated or unsupported.** Nothing is dropped silently, but those items need
  your attention. Examples of judgement calls: a relocation milestone becomes a move on the residency timeline;
  a percentage priority is read from its amount; per-account overrides are kept only where they differ from the
  account's own settings.
- **Interface state.** Chart and table preferences, layout, tour progress and similar settings are ignored.
- **Account state and secrets.** Billing and terms state are ignored. A plugin API key in the file is discarded
  and never read into the report.
- **Results.** Glideworth recalculates with its own engine and tax tables, so projected figures will differ from
  ProjectionLab's even for the same inputs.
- **Starting conditions.** Only the default (live) starting condition is represented.
- **Newer fields.** The importer was built against export format 4.6. A newer export may include fields the
  report lists as unrecognised.
- **Re-importing** the same household needs replace mode.

The importer needs a JSON export file from ProjectionLab. ProjectionLab's plugin interface has an `exportData`
method that returns account data
([Plugin API docs](https://app.projectionlab.com/docs/types/PluginAPI.html), read 16 Nov 2026); we have not
confirmed where its app's menus offer the export, so check its help pages.
